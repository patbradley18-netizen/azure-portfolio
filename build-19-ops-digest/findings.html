Six checks, one email: a weekly operations digest that reads everything and holds no keys

Build #12 put one alert on one number. Eighteen builds later there are four Function apps, a data API, an ingestion pipeline, two GitHub pipelines, a free SQL database with a monthly ceiling and a free ADX cluster with an expiry date. This build asks all of them the same question once a week and sends one red/amber/green email. A Logic App with its own identity does the asking; Azure Communication Services sends the mail; every call is an Entra token, and the recipient is read from the alert action group at run time, so no address is in the template, the workflow or the repo. Anchor phrase: six checks, one email, no keys.

Why it is red: the failed Function requests, and what they were

The digest counted 21 at 00:38 UTC; by the snapshot there were 23. 11 of 23 were the free SQL database waking up: the first connection after auto-pause times out (Win32Exception inside SqlClient). On the data API that reached a caller as an HTTP 500; on the Saturday BLS pull the retry then loaded all 1,528 rows. The other 12 are this week's own build-and-break testing. The digest is right to be red; the line "any failure = red" will be revisited after one quiet week, not before.

The plan was to read the ingestion ledger through the build #13 API. That API takes a function key, and fetching one at run time needs write access to the Function app; reading the three storage counts directly needs only data-reader roles. The two reads outside the resource group are deployed by the operator (sub-roles.bicep): the GitHub identity is limited to rg-azportfolio-b1 on purpose, and this build did not widen it.

The digest-failure alert fired at 2026-10-18 00:25 UTC. A Recurrence trigger with a schedule and no start time runs once the moment it is created — before Azure had finished granting the Logic App its roles, so every read returned 403 (2 s, run Failed). No email was sent (the recipient lookup was one of the 403s); the alert was. The fix is one line, startTime on the trigger. Six metric alerts now exist; ten are free.

In the template, under the gate

The digest is a module of main.bicep, so build #18's pipeline what-ifs it on every push. Against the live group: 0 Create, 0 Delete, 20 Modify, 24 NoChange — the gate stays green. The digest's own Modify rows are the same blind spot build #18 documented (a role assignment's principalId comes from reference()), the container's encryption defaults (now stated), and the workflow change itself. Of the 11 role-assignment Modify rows, six are this build's and the rest are build #18's; all are principalId, which what-if cannot evaluate.
