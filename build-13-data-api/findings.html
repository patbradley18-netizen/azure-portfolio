The warehouse as a product: a public data API, a gateway with two products, and a rebuild that runs itself

Twelve builds produced a county warehouse only its author could query. This one puts an HTTP API on it — Azure Functions with SQL bindings and a managed identity, behind API Management with a keyless public product and a keyed one — and a Durable Functions orchestration that rebuilds the access table state by state every month. The OpenAPI spec is the contract; a test suite holds the gateway to it after every deploy. Anchor phrase: a query becomes an endpoint. The buttons call the live gateway from your browser.

The API

Five read endpoints and two orchestration endpoints, one Function app behind API Management. A call for Marion County, Indiana returns its nearest medical center (Richard L. Roudebush Veterans' Administration Medical Center, 2.7 straight-line miles) and nearest care site (Indianapolis VA Clinic, 1.4 miles); a call for Delaware returns 3 counties and the veteran-weighted mean of 33.5 miles; a point in Indianapolis finds the Richard L. Roudebush Veterans' Administration Medical Center at 8.3 miles. Every response carries the data vintage in meta.source.

Base URL https://apim-azportfolio-b13.azure-api.net/data. Read endpoints go through SQL input bindings (parameterised T-SQL or stored procedures); the Function's managed identity has SELECT on schema col and EXECUTE on two procedures, nothing more.

The gateway

Two products on the same API. public: no key, GET only, 30 calls a minute and 2,000 a day shared by everyone (the Consumption tier has no per-caller counters), responses cached 5 minutes. keyed: a subscription key, 60 a minute and 20,000 a month, and the right to start the rebuild. The Function's host key lives in a secret named value in the gateway; the Function answers nobody else. The gateway also fills in miles, kind and top when a caller omits them, because the stored-procedure binding behind /facilities/near needs all five.

API Management, Consumption tier: first 1,000,000 calls a month free. Policies are XML files in the repo (apim/).

      </when>
    </choose>
  </inbound>
  <backend><base /></backend>
  <outbound>
    <base />
    <set-header name="X-Powered-By" exists-action="delete" />
    <set-header name="Cache-Control" exists-action="override"><value>public, max-age=300</value></set-header>
  </outbound>
  <on-error><base /></on-error>

The rebuild

The rebuild is a Durable Functions orchestration: fan out to 51 state activities, each running col.sp_refresh_access_state with retries, fan in to a run record. The last good run 6fba18a9… rebuilt 3,144 rows across 51 states in 33 seconds; the table matched build #10 to the row afterwards. The first run wrote 0 rows and said so: the activity's SQL binding could not address a plain-string input, so the stored procedure ran with an empty state. The fix was an object input; the activity now fails loudly on zero rows.

POST /refresh (keyed product) starts it; GET /refresh/status/{id} follows it; GET /refresh/runs lists the run records. A timer starts it at 03:00 UTC on the first of the month.

The contract

16/16 checks pass against the live gateway: envelope shape, status codes, validation (400, 404, 405), a known value, the gateway's defaults, ordering, a response-time budget. The same script runs in GitHub Actions after every deploy; a broken contract fails the build.

openapi.yaml
openapi: 3.0.3
info:
  title: azportfolio-data
  version: 1.0.0
  description: |
    Read API over the Azure learning portfolio's county warehouse (schema `col`): distance from every county's
    population center to the nearest VA medical center and care site (build #10), served by an Azure Function
    behind API Management. Straight-line miles. Facilities are VA's VAST extract of 2018-09-29; veterans are ACS
    5-year 2023 B21001. Non-commercial learning project; data public domain.
servers:
  - url: https://apim-azportfolio-b13.azure-api.net/data
paths:
  /info:
    get:
      summary: API info
      operationId: apiInfo
      responses:
        "200": { $ref: "#/components/responses/Envelope" }
  /counties/{fips}/access:
    get:
      summary: One county's nearest VA medical center and care site
      operationId: countyAccess
      parameters:
        - { name: fips, in: path, required: true, schema: { type: string, pattern: "^[0-9]{5}$" }, example: "18097" }
      responses:
        "200": { $ref: "#/components/responses/Envelope" }
        "400": { $ref: "#/components/responses/Error" }
        "404": { $ref: "#/components/responses/Error" }
  /states/{state}/access:
    get:
      summary: Every county in a state, farthest first, with the veteran-weighted mean
      operationId: stateAccess
      parameters:
        - { name: state, in: path, required: true, schema: { type: string, pattern: "^[A-Za-z]{2}$" }, example: "IN" }
      responses:
        "200": { $ref: "#/components/responses/Envelope" }
        "400": { $ref: "#/components/responses/Error" }
        "404": { $ref: "#/components/responses/Error" }
  /facilities/near:
    get:
      summary: VA care sites within a radius of a point (live spatial query)
      operationId: facilitiesNear
      parameters:
        - { name: lat, in: query, required: true, schema: { type: number, minimum: -90, maximum: 90 }, example: 39.9 }
        - { name: lon, in: query, required: true, schema: { type: number, minimum: -180, maximum: 180 }, example: -86.2 }
        - { name: miles, in: query, schema: { type: number, default: 60, minimum: 0, exclusiveMinimum: true, maximum: 500 } }
        - { name: kind, in: query, schema: { type: string, enum: [VAMC, HCC, CBOC, OOS] } }
        - { name: top, in: query, schema: { type: integer, default: 20, minimum: 1, maximum: 100 } }
      responses:
        "200": { $ref: "#/components/responses/Envelope" }
        "400": { $ref: "#/components/responses/Error" }
  /refresh:
    post:
      summary: Start the monthly rebuild orchestration now (keyed product only; the public product answers 405)
      operationId: refreshStart
      responses:
        "202": { description: Durable Functions check-status payload (instance id and status URL) }
  /refresh/status/{instanceId}:
    get:
      summary: Status and output of an orchestration instance
      operationId: refreshStatus
      parameters:
        - { name: instanceId, in: path, required: true, schema: { type: string } }
      responses:
        "200": { $ref: "#/components/responses/Envelope" }
        "404": { $ref: "#/components/responses/Error" }
  /refresh/runs:
    get:
      summary: The last 20 orchestration runs that rebuilt the access table
      operationId: refreshRuns
      responses:
        "200": { $ref: "#/components/responses/Envelope" }
components:
  responses:
    Envelope:
      description: "{ data, meta }"
      content:
        application/json:
          schema:
            type: object
            required: [data, meta]
            properties:
              data: {}
              meta:
                type: object
                required: [version, generated_at]
                properties:
                  version: { type: string }
                  generated_at: { type: string, format: date-time }
    Error:
      description: "{ error }"
      content:
        application/json:
          schema: { type: object, required: [error], properties: { error: { type: string } } }

What this cannot say

The public product's limits are shared by every anonymous caller, not per caller — the Consumption tier has no per-key counters for keyless products — so a busy afternoon can rate-limit a stranger. The orchestration rebuilds a table whose inputs change once a year; the monthly schedule is a demonstration of the pattern, not a need. A cold Flex Consumption app answers the first call in seconds, not milliseconds. Azure Maps was blocked by region policy in build #11; API Management Consumption was not — the difference is the first thing any plan checks now.
