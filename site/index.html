Azure Learning Portfolio

Small, free-tier Azure builds on public data. Each one teaches a Business Analyst skill, ships with its code and an honest README, and ends as a live page here. By Patrick Neil Bradley. Total cost so far: $0.

Build #1: Algorithmic Influence Detector (AID Lite)

Coordinated messaging in a public dataset of state-operator tweets: identical-message templates, a 44-account ring, who amplified whom, one-day blasts, and a control-tested null result against the Congressional Record.

Blob Storage · Azure SQL (free) · Functions · AI Language · AI Search · four stages

Build #2: Veteran employment, pulled weekly from BLS

Five Current Population Survey series for veterans and nonveterans, refreshed every Saturday by a Function whose API key lives in Key Vault and nowhere else.

Functions · Key Vault · Azure SQL (free) · SQL output binding

Build #4: Seven questions, seven queries, seven sentences

The queries a Business Analyst writes against the tables from builds #1 and #2: recession recovery times by veteran status, the Gulf War-era II spike, same-month year-over-year reads, and who produced vs amplified. Each answered in one sentence with its number and its caveat, computed from the result, not typed.

Azure SQL (free) · T-SQL: CTEs, window-style self-joins, FULL OUTER JOIN · no new resources

Build #5: Summarize a public report with Azure AI, with the cost controls first

The BLS veterans employment release through Azure AI Language on the free tier: records estimated before the call (39), a hard cap that refuses to run, a ledger of what the API actually billed (39), and a verifier that exact-matches every sentence and number against the source before the page is built. Includes the tier gate that changed the design and the sentiment signal that was discarded, with the reason.

Azure AI Language (F0) · Entra token auth · estimate, cap, ledger, verify · $0

Build #6: Snapshot to source, a cost-of-living warehouse that checks its own numbers

Two published county cost indices (TSCI, TCBI; 3,222 counties) loaded into the free Azure SQL database as a long-format warehouse with a data dictionary and provenance on every row, next to a fresh pull of the Census inputs they cite. Seven T-SQL questions: 16,084 of 16,110 county-field pairs match the Census to the dollar, the rest are suppressed in both, and the published arithmetic recomputes with zero mismatches.

Azure SQL (free) · Key Vault for the Census key · OPENJSON bulk loads · FULL OUTER JOIN reconciliation · $0

Build #7: Do veteran-heavy counties carry heavier shelter costs? No

One more Census table (B21001, civilian veterans by age) closes the gap build #6 admitted. Five T-SQL questions: burden by veteran-share quintile, the top-20 base counties, the measured age skew (49% of veterans are 65+), and a stratified check that age does not rescue the hypothesis. The lowest-veteran-share quintile, the big metros, carries the heaviest burden; the rest are flat.

Azure SQL (free) · labels fetched from the Census metadata · NTILE windows, stratified comparison · a published no · $0

Build #8: Stratifying is not modelling — tenure, income and size explain the veteran gap away

Build #7's no, now explained: one more Census table (tenure) and four population-weighted regressions with controls added one at a time. For renter burden the veteran-share association goes from −0.68 to −0.02 once ownership, income and population are in; ownership does most of the work. A small negative owner-burden association survives. Associations, not effects, and the page says so.

Azure SQL (free) builds the wide table · statsmodels fits the model locally · WLS, HC1 · $0

Build #9: Measure the renter, not the county — the right outcome and the right denominator

Census B25070 turned into a cost-burden rate with the “not computed” households removed from the denominator (50.4% right, 46.9% wrong), the veteran question re-asked with that outcome, and state fixed effects added. Cost burden: no association. Severe burden: a small negative one survives. States explain more of renter burden than every county control combined. The thread ends here.

Azure SQL (free) · GROUP BY ROLLUP · WLS + state fixed effects · $0

Build #10: Can veterans reach the VA? Spatial SQL and the portfolio as code

Every county’s population center joined to the nearest VA medical center and clinic with the geography type on the free SQL tier. 95% of veterans are within 30 straight-line miles of a VA care site; 57% within 30 miles of a medical center. The veteran-densest counties far from a hospital are military base counties. Plus a Bicep template for the whole portfolio and what what-if said about it.

Azure SQL geography + spatial index · STDistance · Bicep what-if · inline SVG map · $0

Build #11: How much does straight-line lie? Road miles for 895 counties, under a cap and a ledger

Build #10’s distances, checked by road: a seeded stratified sample routed one county at a time with a hard call cap and a ledger reconciled in SQL. The detour index is 1.30 and nearly constant, so straight-line rank order stands and straight-line miles do not. Azure Maps was the plan; the student region policy has no overlap with its regions, so the router is OpenStreetMap’s and the Azure part is the materialised join and the ledger.

Azure SQL materialised join + ledger · estimate → cap → ledger → verify · OSRM · $0

Build #12: Before the bill — the free SQL limit, KQL over the Functions, and an alert that proved itself

The unit that bites on free tiers is the SQL database’s 100,000 vCore-seconds a month. A metric alert now emails at 80,000; set first to a threshold already crossed, it fired, the email arrived, then it was raised. KQL over the workspace the Function wizard created: run history, the one failure (the serverless pause from the other side), and under a megabyte ingested. A workbook ties it together; Bicep now describes it all.

Azure Monitor metric alert + action group · Log Analytics / KQL · workbook · Bicep what-if · $0

Build #16: Who they were, who is left — cohort profiles against civilians their age, and a mortality method that fails honestly

Education, race/ethnicity and sex for the two in-theater cohorts on build #15’s clock, each cell against non-veterans surveyed in the same years and reweighted to the cohort’s age mix: differences with 95% intervals, representation indexes, Cohen’s h. Then the survey’s own weights were tried as a headcount against the SSA life table — and the Vietnam cohort grew for fifteen years, which a closed cohort cannot do. The pipeline now creates tables from the file header; the cohort base is a materialized view.

ADX materialized view · header-driven table creation · SSA life tables + VetPop · two-proportion inference · $0

Build #15: Two wars, matched years — Vietnam and GWOT veterans at the same distance from service

Twenty-eight CPS Veterans Supplements (1985–2025) read on one clock, years since separation, with in-theater cohorts for both wars and non-veterans in the same years as the baseline. An Azure Function submits the IPUMS extract, polls it on a durable timer, lands it in Blob and ingests 3.58 M rows into an Azure Data Explorer free cluster; KQL functions carry every recode. On work the wars look alike; on service-connected disability they are different systems; on prison the published tables support a composition index and little more.

Azure Data Explorer free cluster + KQL · Durable Functions async-job pattern · IPUMS API · Key Vault reference · BJS reference table · $0

Build #14: Every file is guilty until proven innocent — event-driven ingestion with quality gates

A file dropped in an inbox container raises an Event Grid event; a validator Function checks it against a YAML contract (name pattern, row count, schema, value ranges) and either quarantines it with a written reason or queues it for loading. A containerised loader on Azure Container Instances drains the queue, dedupes by content hash against an ingest ledger, re-checks the contract, and loads via OPENJSON; a message that fails five times goes to a poison queue, and Event Grid dead-letters what the validator cannot take. The plan said Container Apps Jobs — the student region policy said no.

Event Grid + Blob events · Functions (Python) · Storage queues + poison · Docker image on GHCR · Azure Container Instances · ingest ledger in SQL · $0

Build #13: The warehouse as a product — a public data API, two gateway products, and a rebuild that runs itself

An HTTP API over the county warehouse: Azure Functions with SQL bindings and a managed identity, behind API Management with a keyless public product (rate-limited, GET only) and a keyed one. A Durable Functions orchestration fans out to 51 states to rebuild the access table and fans in to a run record; the first run “completed” with zero rows and now fails loudly instead. The OpenAPI spec is the contract and a 16-check test holds the gateway to it after every deploy. Buttons on the page call the live API.

Functions HTTP + SQL bindings · Durable Functions · API Management (Consumption) · OpenAPI + contract tests in CI · $0

Build #3: This site

Azure Blob Storage static website, deployed by GitHub Actions on every push to main. GitHub signs in to Azure with OIDC through a managed identity: no deployment token, no secret anywhere. A secret-scan gate runs before every deploy.

Blob static website · GitHub Actions · OIDC federated identity
